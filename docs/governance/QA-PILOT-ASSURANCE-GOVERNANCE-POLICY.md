# QA Pilot Assurance Governance Policy

**Version:** 1.0
**Effective:** 2026-07-20
**Epic:** EPIC-QA-PILOT-ASSURANCE-OPERATIONS-INTEGRATION-1
**Status:** ✅ Authoritative

---

## 1. Purpose

This policy defines the governance framework for the QA Pilot assurance operating layer. It institutionalizes the separation between assurance state, Owner decision authority, and operational measurement established across Phases 1–4 of the Assurance Operations Integration epic.

## 2. Scope

This policy applies to all assurance data generated by, routed through, or presented by the QA Pilot assurance operating layer, including findings, evidence, risk prioritization, Owner decisions, and operational measurements.

## 3. Principles

### 3.1 Projection, Not Decision
The assurance layer is a projection surface. It exposes what is known, validated, requiring attention, and requiring Owner action. It does not auto-resolve findings, infer approval, or hide uncertainty.

### 3.2 Separate Sources of Truth
Each project maintains its own assurance state. The routing layer provides cross-project visibility without merging truth domains or creating a new authority source.

### 3.3 Owner Decision Authority
Only the Owner may:
- Accept or reject findings
- Authorize or deny risk acceptance
- Seal or defer sprints
- Approve or reject release readiness
- Modify governance policies

### 3.4 Evidence-Backed State
All assurance state must trace to a source artifact. Provenance is not optional. Every displayed state must carry a reference to the evidence or lifecycle record that produced it.

### 3.5 Stale State Visibility
Stale or incomplete information must be surfaced, not silently suppressed. Evidence age indicators, unacknowledged finding counts, and pending Owner queue items are mandatory display elements.

## 4. Roles

| Role | Authority | Responsibilities |
|------|-----------|-----------------|
| **Owner** | Full decision authority | Seal sprints, accept/reject findings, authorize risk, approve releases, set policy |
| **Assurance Layer** | Advisory only | Generate findings, track evidence, prioritize risk, present dashboard, measure calibration |
| **Routing Layer** | Discover only | Route assurance state between projects, preserve identity, prevent cross-project mutation |
| **Validation Layer** | Verify only | Run validators, report pass/fail, detect drift, do not mutate |

## 5. Data Governance

### 5.1 Finding Lifecycle
| State | Definition | Valid Transitions |
|-------|------------|-------------------|
| OPEN | Newly created, not yet acknowledged | → ACKNOWLEDGED |
| ACKNOWLEDGED | Seen by Owner, under review | → RESOLVING, → CLOSED |
| RESOLVING | Corrective action in progress | → RESOLVED |
| RESOLVED | Action complete, awaiting verification | → CLOSED |
| CLOSED | Final state — verified and accepted/waived | (terminal) |

### 5.2 Evidence Freshness Thresholds
| Classification | Age | Action |
|---------------|-----|--------|
| Fresh | ≤60 minutes | Current — no action |
| Aging | 61–300 minutes | Monitor — may need refresh |
| Stale | >300 minutes | Refresh required before use in decisions |

### 5.3 Risk Priorities
| Priority | Definition | Owner Response |
|----------|------------|----------------|
| HIGH_ATTENTION | Critical — requires Owner decision | Respond within next operating cycle |
| REVIEW | Requires review — non-critical | Review before next seal |
| MONITOR | Informational — no immediate action | Track — no response required |

## 6. Cross-Project Boundaries

1. No assurance tool writes to another project's data directory.
2. The routing layer reads from project stores; it never writes to them.
3. Project identity is attached to every assurance record and is immutable.
4. Cross-project comparison is aggregation, not merging.
5. Missing project data is displayed as gaps, not inferred as negative results.

## 7. Policy Amendments

This policy may be amended only by the Owner. Amendment proposals should include the rationale, affected principles, and transition plan.
