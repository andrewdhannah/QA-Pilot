## 1. Executive Summary

P7.2-3 revealed that the knowledge findings and governance decisions are separate domains with no connection. This design defines the minimal bridge between them without introducing new authority models or automatic remediation.

**Key Design Principle:** The bridge creates decision **candidates**, not decisions. The Owner remains the sole decision authority.

## 2. Finding Lifecycle (BRIDGE-001)

### 2.1 Finding States

```
DISCOVERED
    ↓
CLASSIFIED
    ↓
REVIEW_REQUESTED
    ↓
OWNER_DISPOSITION
    ↓
RESOLUTION_TRACKED
    ↓
CLOSED
```

### 2.2 State Definitions

| State | Meaning | Transition Trigger | Authority |
|-------|---------|-------------------|-----------|
| DISCOVERED | Finding detected by knowledge substrate | Automated scan | System |
| CLASSIFIED | Finding type and severity determined | Automated classification | System |
| REVIEW_REQUESTED | Finding surfaced for Owner review | Bridge creates decision candidate | System (bridge) |
| OWNER_DISPOSITION | Owner has made a decision | Owner action | Owner |
| RESOLUTION_TRACKED | Resolution evidence recorded | Receipt submitted | System (receipt) |
| CLOSED | Finding fully resolved | All evidence linked | System (verification) |

### 2.3 Critical Invariant

**Finding states are NOT entity lifecycle states.** Findings are observations about entities, not changes to entity lifecycle.

## 3. Decision Candidate Model (BRIDGE-002)

### 3.1 Decision Queue Extension

The existing decision queue item structure is extended with a `finding_ref` field:

```json
{
  "queue_id": "finding-<uuid>",
  "source": "knowledge_finding",
  "entity": "<entity_id>",
  "context": "<finding summary>",
  "impact": "<impact description>",
  "options": [
    {"action": "address", "description": "Create work order to resolve finding"},
    {"action": "dismiss", "description": "Finding is not actionable"},
    {"action": "defer", "description": "Defer to later review"}
  ],
  "recommendation": "<system recommendation>",
  "authority": "Owner",
  "severity": "<info|warning|critical>",
  "finding_ref": {
    "finding_id": "<knowledge_substrate_finding_id>",
    "finding_type": "<orphan_implementation|unreferenced_artifact>",
    "finding_status": "discovered",
    "knowledge_substrate_snapshot": "<hash of finding at creation>"
  }
}
```

### 3.2 Decision Candidate Rules

1. **Source = "knowledge_finding"**: All findings from knowledge substrate use this source
2. **Authority = "Owner"**: All finding-based decisions require Owner authority
3. **Options always include "dismiss"**: Owner can always reject a finding
4. **No automatic remediation**: Bridge never creates work orders automatically

## 4. Owner Disposition Boundary (BRIDGE-003)

### 4.1 Authority Layers

```
Knowledge Layer (Detection)
    ├── Detects anomalies
    ├── Classifies findings
    ├── Explains evidence
    └── NEVER decides action

Governance Layer (Decision)
    ├── Receives decision candidates
    ├── Presents options to Owner
    ├── Records Owner disposition
    └── NEVER executes work

Execution Layer (Action)
    ├── Performs approved work
    ├── Produces resolution evidence
    ├── Reports completion
    └── NEVER initiates governance
```

### 4.2 Disposition Options

| Option | Meaning | Required Evidence |
|--------|---------|-------------------|
| address | Owner authorizes work to resolve | Work order ID |
| dismiss | Owner rejects finding as non-actionable | Dismissal rationale |
| defer | Owner defers decision | Deferral reason + review date |

### 4.3 Disposition Receipt

```json
{
  "receipt_type": "finding_disposition",
  "finding_id": "<knowledge_substrate_finding_id>",
  "decision_candidate_id": "<queue_id>",
  "owner_action": "<address|dismiss|defer>",
  "rationale": "<owner provided rationale>",
  "timestamp": "<ISO 8601>",
  "evidence_refs": ["<work_order_id>|<dismissal_receipt_id>"]
}
```

## 6. Authority Analysis (BRIDGE-005)

### 6.1 Authority Boundaries Preserved

| Layer | Authority | Boundary |
|-------|-----------|----------|
| Knowledge | Detect, classify, explain | No action authority |
| Governance | Decide, authorize, record | No execution authority |
| Execution | Perform, report | No governance authority |

### 6.2 No Authority Expansion

The bridge does NOT introduce:
- ❌ Automatic decision making
- ❌ New authority roles
- ❌ Autonomous remediation
- ❌ Entity lifecycle changes
- ❌ Governance bypass

### 6.3 Bridge Authority

The bridge itself has **no authority**. It is a **data transformation** that:
1. Reads findings (knowledge layer)
2. Creates decision candidates (governance layer)
3. Records linkages (evidence layer)

The bridge never decides, authorizes, or executes.

## 8. Design Summary

### 8.1 What the Bridge Does

1. **Transforms** knowledge findings into decision candidates
2. **Preserves** the finding reference in the decision queue
3. **Records** the linkage between finding and decision
4. **Enables** Owner disposition through existing mechanisms

### 8.2 What the Bridge Does NOT Do

1. **Does NOT** make decisions
2. **Does NOT** execute work
3. **Does NOT** bypass governance
4. **Does NOT** introduce new authority
5. **Does NOT** automate remediation

### 8.3 Key Design Invariants

```
Finding
    ↓
Decision Candidate (not decision)
    ↓
Owner Decision (sole authority)
    ↓
Disposition Receipt (evidence)
    ↓
Resolution Evidence (if address)
    ↓
Closure Receipt (verification)
```
