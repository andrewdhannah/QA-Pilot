# P7.1-TEST-001 — Cross-Layer Governance Validation Suite

**Sprint ID:** P7.1-TEST-001
**Project:** qa-pilot
**Phase:** Phase 7 — P7.1 Cross-Project Trial
**Status:** PLANNED — awaiting Owner authorization

**Authority Scope:** restricted

---

## Objective

Validate that the existing governance/qualification mechanisms compose correctly under controlled validation. Prove the testing infrastructure works as a cohesive system, not isolated components.

**This is not test infrastructure expansion.** It is a bounded validation experiment with explicit evidence boundaries.

## Governing Question

Does the existing validation infrastructure compose into a coherent, deterministic assurance stack without duplicating authority or masking failures?

## What This Proves (and Does Not Prove)

**Proves:**
- New components have isolated tests
- Integration chain executes deterministically
- Existing behavior remains unchanged
- Five dimensions remain independent
- Qualification authority boundary holds
- Legacy migration remains reproducible
- Replay produces identical results
- Tampered state is detected
- Unauthorized mutation is prevented
- Cross-instance state contamination is prevented

**Does NOT prove:**
- The system is operationally effective
- Real cross-project work produces useful outcomes
- Evidence changes Owner decisions

P7.1 still needs actual cross-project work to answer those questions.

## Scope

### In Scope

1. Unit tests for 6 new components (LVC-001 + GPI-001)
2. Integration chain test (registry → reader → qualify → validate → receipt)
3. Regression tests (existing behavior unchanged)
4. Adversarial tests (11 attack scenarios)
5. Cross-instance isolation test
6. Layered evidence preservation per test
7. Aggregate projection

### Out of Scope

- New assurance primitives
- New governance authority
- New validators beyond what exists
- Runtime qualification changes
- Registry changes
- Architecture expansion

---

## Test Structure

Each test produces layered evidence:

```
Test
 ├── input/state reference
 ├── validator executed
 ├── expected result
 ├── actual result
 ├── evidence reference
 └── receipt/result
```

Aggregate projection on top preserves diagnostic value.

## Work Packets

### WP-TEST-001 — Layer 1: Unit Tests

**Purpose:** Verify each new component independently.

**Components to test:**
1. `governance_state_reader.py` — read, list, validate, get-dimension
2. `runtime_qualification.py` — evaluate, batch, status
3. `validate-qualification-authority.py` — boundary check
4. `validate-lifecycle-vocabulary.py` — conflation detection
5. `migrate-governance-state.py` — migration reproducibility
6. `lifecycle-vocabulary.schema.json` — schema validation

**Acceptance Gates:**
- TEST-001: All new components have isolated tests

### WP-TEST-002 — Layer 2: Integration Chain

**Purpose:** Test the full path from canonical registry to qualification receipt.

**Path:**
```
Canonical Registry
      ↓
State Reader
      ↓
Qualification
      ↓
Qualification Result
      ↓
Authority Validation
      ↓
Evidence / Receipt
```

**Test both valid and invalid compositions.**

**Acceptance Gates:**
- TEST-002: Integration chain executes deterministically

### WP-TEST-003 — Layer 3: Regression

**Purpose:** Establish behavioral equivalence before/after LVC-001 and GPI-001.

**Before:** existing qualification behavior
**After:** existing qualification behavior + canonical five-dimensional context

**Expected result:** behavioral equivalence where behavior was not intentionally changed.

**Acceptance Gates:**
- TEST-003: Existing behavior remains unchanged
- TEST-006: Legacy migration remains reproducible
- TEST-011: Existing validators/runners remain green

### WP-TEST-004 — Layer 4: Adversarial

**Purpose:** Attempt attacks against the governance boundary.

**Attack scenarios:**
1. lifecycle → qualification substitution
2. qualification → lifecycle mutation
3. health → execution authorization
4. execution policy → qualification inference
5. entity type → authority inference
6. forged canonical-state input
7. modified qualification snapshot
8. replay with altered state
9. legacy-field manipulation
10. cross-instance state injection
11. receipt/state mismatch

**Expected behavior:** Invalid input → Detection → Finding → NO unauthorized mutation

**Acceptance Gates:**
- TEST-004: Five dimensions remain independent
- TEST-005: Qualification authority boundary holds
- TEST-007: Replay produces identical results
- TEST-008: Tampered state is detected
- TEST-009: Unauthorized mutation is prevented

### WP-TEST-005 — Cross-Instance Isolation

**Purpose:** Verify that qualification against Instance B never acquires state from Instance A.

**Acceptance Gates:**
- TEST-010: Cross-instance state contamination is prevented

### WP-TEST-006 — Evidence and Aggregate

**Purpose:** Preserve layered evidence and produce aggregate projection.

**Acceptance Gates:**
- TEST-012: Failures identify the responsible layer
- TEST-013: No duplicate governance authority introduced
- TEST-014: Test results themselves are evidence-backed
- TEST-015: No architecture expansion required
