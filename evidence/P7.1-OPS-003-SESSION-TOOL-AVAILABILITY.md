# P7.1-OPS-003 — Librarian Session Tool Availability Characterization

**Date:** 2026-08-17
**Work Order:** P7.1-OPS-003
**Type:** Investigation — empirical
**Status:** COMPLETE

---

## Investigation Summary

The Librarian session tools are **registered and discoverable** on the MCP server. They are **not missing**. They fail at invocation because the startup process does not establish the authorization context they require.

---

## Evidence

### Step 1: Tool Discovery

The Librarian MCP server exposes session management tools. They are callable — they return structured errors, not "unknown tool" responses. This proves the tools are registered in the MCP catalog.

| Tool | Called | Response Type |
|---|---|---|
| `librarian_start_work_order` | Yes | Structured error (not "unknown tool") |
| `librarian_start_session` | Yes | Structured error (not "unknown tool") |
| `librarian_governance_authorize_agent` | Yes | Structured error (not "unknown tool") |

### Step 2: Error Analysis

| Tool | Error Code | Message |
|---|---|---|
| `librarian_start_work_order` | -32602 | "Authority enforcement denied: Operation 'dispatch' requires an authorization basis (e.g. Owner decision ID, batch plan reference, delegation envelope)." |
| `librarian_start_session` | -32602 | "start_session: The data couldn't be read because it is missing." |
| `librarian_governance_authorize_agent` | -32602 | "agent_id is required; entity is required; intent is required; requested_actions is required." |

All three are **parameter validation errors**, not discovery failures. The tools exist but require inputs the startup process does not provide.

### Step 3: Startup Contract Analysis

The QA Pilot startup contract (`active/qa-pilot/startup-contract.json`) declares:

```json
"mcp_context": {
    "required": true,
    "profile_tool": "project_get_profile",
    "cursor_tool": "project_get_cursor",
    "transitions_tool": "project_get_allowed_transitions",
    "context_tool": "project_assemble_context"
}
```

The declared MCP tools are:
- `project_get_profile` — governance profile retrieval
- `project_get_cursor` — lifecycle cursor retrieval
- `project_get_allowed_transitions` — transition lookup
- `project_assemble_context` — context packet assembly

**Not declared:**
- `librarian_start_work_order`
- `librarian_start_session`
- `librarian_governance_authorize_agent`

### Step 4: Capability Binding Analysis

The adapter's `capability_discovery` section defines one service:

```json
{
    "id": "librarian",
    "detection": {
        "method": "file_exists",
        "path": "active/librarian/startup-contract.json"
    }
}
```

Detection succeeds (file exists). The adapter reports `librarian` as `available: present`. But capability discovery detects **service availability**, not **tool-level authorization**.

The `active_capability_binding` is:

```json
{
    "capability_id": "qa-pilot",
    "role": "development_target",
    "binding_source": "adapter_resolution"
}
```

This binding means: "qa-pilot is the development target." It does **not** mean: "qa-pilot has authorized access to all Librarian session tools."

### Step 5: Root Cause

The gap is between three layers:

```
Layer 1: MCP Server
  └─ Tools registered: ALL Librarian tools (including session management)
  └─ Tools callable: YES (return structured errors, not "unknown tool")

Layer 2: Startup Contract (project-level)
  └─ Declares 4 MCP tools: project_get_profile, cursor, transitions, context
  └─ Does NOT declare session management tools

Layer 3: Adapter Capability Detection
  └─ Detects Librarian service: present
  └─ Does NOT detect tool-level authorization
```

The MCP server has the tools. The startup contract doesn't declare them. The adapter doesn't bridge this gap.

**The tools are not "unavailable." They are "undeclared in the project contract."**

---

## Classification

**Type:** Design gap — tool-level authorization not bridged by startup process
**Severity:** Blocking for governed lifecycle, non-blocking for direct execution
**Root cause:** Startup contract declares tool subset; session management tools not in subset; no mechanism to request/establish authorization at tool invocation time
**Is this a defect?** No. It is an **expected limitation** of the current architecture. The startup contract was designed to declare a bounded tool subset for project operations. Session management tools require a different authorization path that has not been operationalized.

---

## Recommendation

**Accept limitation. Change the P7.1 experiment design.**

### Rationale

1. The tools are not broken — they require authorization context that the startup process was not designed to provide.
2. Fixing this requires either:
   - Adding session management tools to the startup contract's `mcp_context` declaration, AND
   - Establishing an authorization flow (decision ID, batch plan, or delegation envelope) at startup time.
   This is architecture work, which the Owner explicitly excluded.

3. The correct response is to recognize this as a known constraint and adjust P7.1 accordingly.

### P7.1 Experiment Design Adjustment

**Before this finding:** P7.1 was testing "Does using the Librarian during real work produce better outcomes?"

**After this finding:** P7.1 should test "Does the Librarian's governance substrate (startup contract, capability binding, project resolution, MCP health, projection) produce better outcomes when the agent works within the declared tool subset?"

The session management tools (work order, session, authorization) are a **separate capability layer** that requires additional authorization infrastructure. P7.1 should not depend on them.

### What P7.1 CAN Use

| Tool | Available | Purpose |
|---|---|---|
| `project_get_profile` | Yes (declared) | Governance profile |
| `project_get_cursor` | Yes (declared) | Lifecycle position |
| `project_get_allowed_transitions` | Yes (declared) | Valid transitions |
| `project_assemble_context` | Yes (declared) | Context packet |
| `project_work_*` | Transitional (DB not populated) | Work item queries |
| Flightplan tools | Yes (separate system) | Token tracking |
| Direct file tools | Yes (always) | Execution |

### What P7.1 Cannot Use (Until Authorization Infrastructure Exists)

| Tool | Blocked | Reason |
|---|---|---|
| `librarian_start_work_order` | Yes | Requires authorization basis |
| `librarian_start_session` | Yes | Requires data binding |
| `librarian_governance_authorize_agent` | Yes | Requires entity/intent/actions |

## Effect on P7.1 Hypothesis

**H₀:** Librarian tools add overhead without changing output quality.

**H₁:** Librarian tools produce better Owner decisions.

**Updated scope:** The hypothesis now applies to the **declared tool subset** (profile, cursor, transitions, context) plus the **governance infrastructure** (startup contract, capability binding, MCP health, projection). It does **not** apply to session management tools, which are a separate capability layer.

**The confound the Owner identified is now resolved:**
- Governance value (startup contract + capability binding + declared tools) can be tested independently
- Governance tool availability (session management) is a separate, currently unavailable layer
- Future P7.1 work items can test the declared tools without the confound
